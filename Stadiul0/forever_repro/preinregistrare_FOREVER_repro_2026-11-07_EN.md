# Preregistration of the FOREVER reproduction with their code (7 Nov 2026, BEFORE running)

**Why:** the main limit left after the decisive tests and after SuperNI: the comparisons with FOREVER (arXiv:2601.03938) were made with our port, not with their code. Requested by the user ("Reproduce with their code", "Full fidelity, ~17 h").

**Code and environment:** the working copy `Stadiul0/forever_repro/` of their repository (github.com/WoodScene/FOREVER, commit `bbeb549a21e5…`; the originals in `D:\Time\_date\FOREVER_bbeb549\`, checked with the git hashes). The separate environment `D:\Time\_venv_forever` with the versions of their `requirements.txt`: torch 2.8.0+cu128, transformers 4.57.0, peft 0.17.1, accelerate 1.10.1, datasets 4.1.1, numpy 1.26.4 etc. (`pip_freeze_venv_forever.txt`); Python 3.12.

**The adaptations (the only changes to their code):**
1. `TRANSFORMERS_CACHE` / `AutoConfig.default_cache_dir`: a local path instead of `/workspace/...`;
2. in `generate_avgPerf.py` and `generate_bwt.py`: the path of the test files comes from `FOREVER_DATA` (`data_longsequence`); the original hard-codes `../data_superni`, so it could not evaluate the "long sequence" benchmark;
3. running with `python` instead of `torchrun --nproc_per_node=1` (one GPU); `PYTHONIOENCODING=utf-8` (the Windows console); `HF_HUB_OFFLINE=1`; the file name: their launch script calls `finetune_cl_ours_qwen.py`, which does not exist in the repository; we run `finetune_cl_our_qwen.py`;
4. torch 2.8 on Windows, an RTX 3050 4 GB laptop (theirs: Linux, another GPU). Their code is not deterministic (fp16, no deterministic algorithms), so a repetition gives slightly different results.

**The runs:** order 4 [`dataset_id` 4 of their repository, the "Standard CL" sequence; order 1 of the paper, Appendix G, Table 14] ("Standard CL": dbpedia → amazon → yahoo → agnews), the exact arguments of `scripts/run_train_cl_ours_qwen.sh`: `--num_epochs 10 --first_task_epochs 60 --group_by_length --lora_target_modules ["q_proj","v_proj"] --micro_batch_size 4 --batch_size 32 --max_input_length 512 --memory_epochs 2 --steps_per_day 24 --memory_data_ratio 2`. After each of tasks 0–2: `generate_bwt.py` on that task; after the last: `generate_avgPerf.py` on all 4. Evaluation with their `eval_avgPerf_longsequence.py` and `eval_bwt_longsequence.py`.
- **R1, the reproduction:** their code unchanged (the τ clock).
- **R2, the clock swap:** `finetune_cl_our_qwen_clock.py`, generated by `make_clock_variant.py`; the only change: the counter that drives replay (`DriftRecorderCallback.tau`) advances by η·‖m̂‖ (the bias-corrected AdamW first moment) instead of ‖Δθ‖. The actual norm is kept in `tau_true`, and the intensity μ (hence β) is still computed from ‖Δθ‖, as in the original.

**The criteria (fixed now):**
- **R1 reproduces FOREVER** if OP on order 4 (their script `eval_avgPerf_longsequence.py`, exact match) is within **±5 points** of **72.9** (Table 1 of the paper, the mean over 3 orders). Also reported: BWT (the paper: −4.7) and OP computed with the label extraction of their BWT script (more lenient).
- **R2 against R1** (a single pair, descriptive, no interval): **equivalence** if |OP(τ) − OP(η‖m̂‖)| ≤ 2 points; **τ better** if the difference is > 2; **η‖m̂‖ better** if it is < −2. The same report for BWT.
- **Secondary, the reconstruction in their code:** in run R2, the R² (OLS) of the rate of ‖Δθ‖ over 8-step windows, from the increase of the η‖m̂‖ clock in the same window; reported (our benchmark: ≥ 0.90).
- **If R1 does not reproduce** (OP outside ±5): R2 is reported only descriptively, and the conclusions about FOREVER remain limited to our port.

**Estimated duration** (speeds measured with their code: ~5.5–7 s per step, ~0.35 s per generated example): per variant ~5 h of training + ~1.4 h of BWT generation + ~1.6 h of OP generation ≈ **8 h**; in total **~16–17 h**.
